# Durable requests integration

The request implementation is transport-independent after authentication. WhatsApp creates a `RequestJournal` entry in `whatsapp/requests/<sha256>.json` before inbox publication. Telegram uses the same journal after its explicit pairing. Any transport may use the same journal only after its own selected-chat authorization and must supply explicit `provenance`, a transport credential fingerprint, and its bound recipient route. Route and credential scope are required for context and summary cursors; the WhatsApp adapter continues to derive its scope from the authenticated account and does not change `currentRoute()`.

## Parent-facing APIs

- `new Bridge({... , summary(command) })`: `summary` is optional. If absent, the backward-compatible `status(command)` callback is used. Commands are `status`, `pending`, `blocked`, `decisions`, `last result`, and `more`. `more` uses a durable per-route cursor.
- `FirstmateAdapter.progress(key, state, text)`: records and queues explicit owner progress. States accepted here are `picked-up`, `working`, `waiting`, and `failed`. It rejects transitions outside the lifecycle graph below; an explicit `picked-up` may resume a `waiting` request. Use `reply(key, text)` for final successful completion; `reply` durably changes the request to `completed` after its deterministic queue entry exists.
- `await FirstmateAdapter.maintain(options?)`: call from the parent tick. It returns `{key,state,evidence,code,dedupeId,text}` reports. After five minutes by default it can re-ring the **same existing inbox note/wake** at most three times, only for this adapter's current authenticated route. It never republishes a note, executes its body, takes the bridge/owner lock, or changes AFK. Watcher-stale wording is used only when `.last-watcher-beat` supplies stale evidence; absent evidence and wake errors explicitly say state is unknown.
- `FirstmateAdapter.notifyMaintenance(report)`: queues one route-bound status reply using the report's stable `dedupeId`; repeated calls deduplicate. Parent should call this only for the selected report it wants surfaced, rather than generating a new notification ID on every tick.
- `await FirstmateAdapter.summary(command)`: recorded lifecycle summaries. Every result is page-bounded and `more` resumes the same durable query on the same credential/recipient route. `status` labels Firstmate fleet status separately. `decisions` uses `fm-whatsapp-decisions.sh`, which reads open decisions through Firstmate's installed status parser without requiring AFK or extension enablement.
- `RequestJournal` and `REQUEST_STATES` are exported by `bin/fm-whatsapp/requests.mjs` for authenticated transport integration.

Lifecycle is `received -> picked-up/working/waiting/completed/failed`, then `picked-up/working/waiting -> picked-up/working/waiting/completed/failed` as applicable. A terminal `completed` or `failed` record is immutable: any conflicting final result is refused without changing durable history, and only exact replay of the recorded final text stays idempotent. An explicit `picked-up` may resume an automatically diagnosed `waiting` request. Saving a note and sending the immediate receipt leave it at `received`; neither is completion. Inbox handled evidence may advance `received` to `picked-up`. Only explicit `progress` or final `reply` records later states.

Quoted outbound context is loaded only from the durable sent record and must match the exact account/recipient route. Decision replies additionally require persisted `event.kind === "decision"`, exact task/key metadata, and a still-open matching event. Stale and ambiguous approval-like replies are refused locally; the extension never performs a decision. Accepted exact replies are notes directing Firstmate to its normal decision handling.

Unquoted followups receive a strictly bounded aggregate of recent request text and recorded progress/final answers, including the most recent completed result as well as recent open work. Content is read from sanitized durable lifecycle records and is isolated by transport credential and recipient. This survives restart and cannot cross a recipient or credential change. Summaries can expose the complete recorded answer over multiple `more` pages without silently slicing it.

## Size boundaries and ordering

All transport sizing lives in `core.mjs`: `chunkText` splits deterministically into lossless, size-bounded parts that never break a surrogate pair or CRLF; `truncateText`/`safeBoundaryEnd` truncate on whole-character boundaries; `MAX_TEXT` remains the per-message transport bound. `reply` records the full result in the journal (up to the stdin byte cap) while queueing ordered parts whose queue identities are pure functions of `(request key, full result text, part index)`, so replays deduplicate and conflicting results are refused as before. Outbox jobs carry a durable `seq` assigned under the queue lock; `Bridge.flush` and the Telegram fallback deliver in `(seq, created, key)` order via `outboundOrder`, and a waiting part holds later parts of the same `part.family` without blocking unrelated replies.
